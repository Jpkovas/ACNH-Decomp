# ACNH-Decomp: coordination of parallel work

The owner requested a larger team with separate local/cloud threads on
2026-10-13. Coordination remains in thread
`01a13734-dae4-73f2-87e4-e4a88be7d1da`.

The full objective remains native playable Windows reconstruction of ACNH,
starting with 1.0.0 while preserving 3.0.3 research. Boot, gameplay/tutorial,
input, audio and real save/reload must work. Automatic ARM64 lifting,
interpretation and emulation support research and do not complete decompilation.
Elysium remains excluded. Proprietary inputs and artifacts stay private.

## Ownership and integration

The coordinator owns generator, shared CMake, production runtime/vendor,
default binaries, integrated coverage, publication and whole-game execution.
Workers must use new files in their assigned area, or private copies and exact
patch proposals. No reset, clean, broad checkout, unrelated staging or push.
Existing uncommitted work must be preserved. A worker finding an overlap stops
the conflicting edit and documents the overlap before requesting coordination.

Separate local threads can read local private inputs. Cloud threads receive
only public source, own interfaces, aggregate facts and synthetic data. Never
upload dumps, keys, firmware, assets, captures, lifted code or Ghidra databases.
Cloud deliverables are imported only after independent local review and tests.

Workers finish with [the delivery contract](team/DELIVERY-TEMPLATE.md).
The coordinator tracks task IDs, ownership, status and artifact paths in
`private/team/registry.json`. Every task contributes to the same objective;
completion of a subtask is not completion of the game goal.

## Test scheduling

Only the coordinator launches or controls a real game process. Before any
benchmark, large oracle corpus or compilation, inspect
`private/team/TIMING-LOCK.json`. An active lease means pause heavy work, continue
reading/docs and ask coordination before the next heavy batch. A stale lease
is not permission to remove it or kill a process. Use a separate scratch/output
directory per task. No worker replaces binaries used by a running session.

Runtime tests and original-derived fixtures run locally. Cloud testing uses
only own/synthetic data. Live game tests require exact module/runtime/backend
hashes, flags, PID, terminal report and observed visual/input/audio evidence.
Timeout termination is recorded as forced termination, never normal exit.

## Acceptance stages

1. Prepared source: implementation exists; no correctness claim.
2. Isolated tested: exact artifacts and own/original-oracle scope are documented.
3. Independently reviewed: another reviewer checks mechanisms and limits.
4. Integrated candidate: actual generated-module dispatch/provenance and gates
   pass against the exact candidate DLL. Default promotion remains separate.
5. Real execution verified: affected scene and behavior work with exact hashes.

Coverage counts only complete reconstructed original bodies integrated and
validated in the real module. Isolated candidates, dependencies, guarded or
partial entries, infrastructure, automatic lifting and synthetic cases are
separate. Source byte intervals must not overlap. Every acceptance report states
what remains original, interpreted, modeled, stubbed or untested.
