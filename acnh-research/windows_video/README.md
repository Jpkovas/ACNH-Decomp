The Windows bridge builds the pinned FFmpeg 9.0.2 H.264 decoder as native x64 code. NVDEC register jobs are serviced by libavcodec, decoded pictures are written to the guest NV12 surfaces, and VIC composes those surfaces. This is host service emulation supporting the interim bridge. It does not recover game source and does not increase decompilation coverage.

Run `scripts/prepare_windows_video.ps1` to verify the portable NASM 3.02 distribution, executable and BSD license against `config/tool-nasm.lock.json`. The POSIX shell and GNU make come from the already pinned llvm-mingw distribution. `scripts/build_windows_bridge.ps1 -Backend vulkan -Jobs 4` enables video by default and limits FFmpeg compilation to four jobs. `-NoVideo` explicitly disables it for diagnostic builds. FFmpeg's upstream archive URL and SHA-256 remain pinned in ScarletNX's dependency configuration.

Run `scripts/test_windows_video.ps1` after building the runtime. The fixture generates its own H.264 I_PCM bitstreams and calls the actual NVDEC and VIC implementations with bounded synthetic memory. It validates 11 cases: three input framing forms on two decoder channels, six RGBA/BGRA surfaces and two failure statuses. Decoded NV12 samples, the independent block-linear bit permutation, output pixels and 64 zero padding bytes are checked. A length-prefixed 390-byte NAL exercises the ambiguous `00 00 01` prefix that previously broke MP4 decoding. No game assets or original ARM instructions are involved.

This fixture covers 16×16 progressive, 8-bit 4:2:0 I_PCM pictures. It does not validate CABAC, interframe reference ordering, every VIC format, scaling, codecs other than H.264, or the game's movie sequence. The game run through the affected scene is required separately. The decoder has not been verified as bit-exact against Switch hardware.
